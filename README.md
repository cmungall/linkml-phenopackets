 * [https://cmungall.github.io/linkml-phenopackets/](https://cmungall.github.io/linkml-phenopackets/)

## What is this repo and how was it made?

This is a rendering of the [phenopackets](https://phenopacket-schema.readthedocs.io/) schema in LinkML.
It is NOT the official GA4GH phenopackets schema.

The intent is to demonstrate some of the tooling and integrative capabilities of LinkML over Protobuf, in particular:

- Additional validation not possible in Protobuf, including:
    - required fields
    - ontology constraints
- Generation of python classes and tooling
- Export/Import phenopackets from to and from RDF
- Semantic annotation of schemas
- Cross-schema integration

The LinkML schema is generated using a script [proto2linkml](util/proto2linkml.pl) that converts from the Protobuf source. This makes
use of specific *conventions* in the Protobuf source, such as the use of particular controlled
keywords in `//` comments. As such, this code is *not* generalizable to other protobuf schemas.

Note we intentionally don't use out of band-info. We have not done additional curation based on the `.rst` docs,
it comes from protobuf.

### Which version of Phenopackets is this?

The schema corresponds to [release 2.0.0](https://github.com/phenopackets/phenopacket-schema/releases/tag/2.0.0)
of phenopacket-schema. The root module, [phenopackets.yaml](src/phenopackets/schema/phenopackets.yaml), names the
protobuf file of that release as its `source`.

The release is set in the [Makefile](Makefile), together with the two things that the release itself depends on:
the commit of [vrs-protobuf](https://github.com/ga4gh/vrs-protobuf) that it includes as a git submodule, and the
version of Protobuf that its `Timestamp` and `Any` types come from. To generate the schema again, and then
everything that is derived from it:

```bash
make auto deploy    # downloads the protobuf files of the release and converts them
make descriptors    # only needed after changing the release or a pin, see below
make all py src/phenopackets/pydantic/model.py
make test sync-examples
```

`make test` compares the schema with what `protoc` makes of the same protobuf files, which is stored in
[tests/input](tests/input) by `make descriptors`. Every message, field, oneof and enum of the release has to be
in the schema, with its documentation, and the generated modules may not define anything else. See
[tests/test_schema](tests/test_schema/test_protobuf_conformance.py), which also describes how each protobuf
construct is translated. `make test` also generates the Python classes again, and fails when they differ from
the ones in the repository.

### Differences from protobuf

The schema describes a phenopacket as it is written in JSON or YAML: attributes are named after the JSON names
of the fields (`individual_id` is `individualId`, and the VRS `_id` fields are `Id`). A few things are not
carried over exactly:

- **Requirement levels.** A field is required only if its protobuf comment says `REQUIRED`. The documentation
  of the release marks many more fields as required or recommended (`Phenopacket.id` for example). These
  are not in the protobuf files, and so they are not in the schema.
- **Maps.** `File.fileAttributes` and `File.individualToFileIdentifiers` are `map<string, string>` fields.
  They are dictionaries of `DictionaryEntry` objects. The `{key: value}` form of protobuf is valid; the Python
  classes write `{key: {key: ..., value: ...}}`.
- **64 bit integers.** `VcfRecord.pos` and the positions and counts in VRS are integers. Protobuf writes them as
  strings in JSON (`"pos": "45989626"`), which the Python classes convert, but which `linkml-validate` reports
  as errors. Convert such a file with `linkml-convert` before validating it.
- **Timestamps** are strings, as they are in JSON.
- **`Extension.value`** is a list of strings. In release 2.0.0 it is a list of `google.protobuf.Any`. Later
  versions of phenopacket-schema (2.0.1 and up, used by phenopacket-tools) changed it to a single string.
- **Oneofs.** A `oneof` is a rule that says that exactly one of its fields is required, which is how the
  documentation describes them. Protobuf also accepts a message with none of them. Neither `linkml-validate`
  nor the Python classes check these rules.

## Ontology Enhancements

The file [cv_terms.yaml](https://github.com/cmungall/linkml-phenopackets/blob/main/src/phenopackets/schema/cv_terms.yaml)
is hand-curated, rather than derived from the YAML. It is based on: [recommended ontologies](https://phenopacket-schema.readthedocs.io/en/latest/recommended-ontologies.html)
from the official phenopackets repo. It makes use of *dynamic enums* which allows for more advanced
ontology checking; for example:

* Uberon anatomy terms must be found under the "anatomical entity branch"
* HPO abnormality terms must be found under the "phenotypic abnormality branch"

etc

We also include [constants.yaml](https://github.com/cmungall/linkml-phenopackets/blob/main/src/phenopackets/schema/constants.yaml)
which is a direct transform from the phenopackets-tools repo.

## How to use this repo

You can browse the [schema docs](https://cmungall.github.io/linkml-phenopackets/) which are generated from the LinkML
schema.

You can also explore the schema in the [schema](src/phenopackets/schema) directory.

As part of the build process, we also validate and convert all canonical Phenopacket examples into YAML, JSON,
and RDF.

* [examples/](examples/) - converted examples

You can also use the generated python classes in combination with the linkml-runtime. Note that we have NOT
released this to PyPI to avoid confusion with official Phenopackets libraries, so to run this you will need to clone
the repo and install it locally.

```bash
poetry install
```

There will also be demonstrator Jupyter notebooks here:

- [notebooks](src/docs/notebooks) directory

### Building the documentation

The [schema docs](https://cmungall.github.io/linkml-phenopackets/) are built by [mkdocs](https://www.mkdocs.org/)
from the pages in [src/docs](src/docs) and the pages that `gen-doc` generates from the schema:

```bash
make serve    # generates the pages in docs/, and shows the site on http://127.0.0.1:8000/linkml-phenopackets/
```

The generated pages use the templates that come with LinkML, except for the index page, which has a
template in [src/doc-templates](src/doc-templates). The diagram of the whole schema has a
[page of its own](src/docs/schema-diagram.md), which shows the output of `gen-erdiagram`.

On a file system that does not distinguish upper and lower case, as is usual on macOS, the page of a class
overwrites the page of a slot with the same name (`Age` and `age`), and mkdocs reports links that it cannot
find. The site that is published is built on Linux, and has both pages.

A push to `main` that changes the schema or the documentation publishes the site, see the
[workflow](.github/workflows/deploy_documentation.yml).

## Validation

Use `p3 validate` to validate objects. This goes beyond what can be done with JSON-Schema alone, and
includes ontology validation using OAK and CURIE validation using BioRegistry.

See [this notebook](https://github.com/cmungall/linkml-phenopackets/blob/main/src/docs/notebooks/OAK.ipynb)

## Repairing ontology terms

Phenopackets include ontology terms, which are liable to become stale.

This toolkit uses OAK to assist in auto-migration of obsoletes or stale labels.
